Why Fuzzing Matters?

Created on July 11, 2025

2025   ·   code   ·   reflection

Among different software testing techniques, automated testing, stands out due to its automatic input generation, test execution, and reporting that accelerates the software development lifecycle. Fuzz testing, aka fuzzing, is one of the most widely used automated testing approaches, popularized by Google’s OSS-Fuzz framework.

The concept of fuzzing was originally crafted in an operating system course in 1980s by Prof. Barton Miller. The idea was to randomly generate inputs to test programs while developers usually design test cases based on programs in traditional testing methods. Random inputs, absurd as the term might sound, surprisingly work well to expose software defects and vulnerabilities.

Even though human written test cases can satisfy specific testing intents of developers, randomly created inputs sometimes allow for a better exploration of the entire input space, thus having a higher chance of exposing bugs hiding deeper in program paths. An analogy that comes up in my mind is like walking in a corn maze, when you strategically pick a path from the entry point and stick with it, it might lead you to a dead end or requires you to finish your depth first search until you find a way out. However, if you start from random positions in a maze, you might discover the exit at the next corner. The point here is that random input generation may cover cases that developers are unable to think of or corner cases that might be ignored when mannually writting test inputs.

Testing Speed

Another benefit of fuzz testing is that while a human may need hours of thinking to write careful test cases, a machine can generate hundreds of inputs in seconds. Moreover, one can execute tests on programs and collect runtime data without human in the loop, boosting the development efficiency as developers can focus on other tasks and go back to the fuzzing results later for debugging. With thousands even millions of executions per minute, the amount of test inputs that a fuzzer can execute on the program (PUT) is enormous, leading to a faster speed at pruning the input space and exposing vulnerabilities.

“Not just Random”

Complex programs often involves conditionals or more complicated constructs. Thus, executing purely randomly generated inputs is sometimes a waste of time. For example, if the program requires a numeric input greater than 1000, then any number generated that is smaller than 1000 and any other types of non-numeric inputs will be rejected immediately without reaching deeper in the program. To generate more “useful” inputs, or say, the inputs that can explore more of a program’s paths, people come up with different fuzzing techniques.

In blackbox fuzzing, the fuzzer has no knowledge of the PUT and generates inputs randomly. The other end of spectrum is whitebox fuzzing, where the fuzzer has complete knowledge of the PUT, and often relies on program analysis techniques to generate inputs that can satisfy complicated program logics. Greybox fuzzing, falls in between these two techniques. A greybox fuzzer does not generate random inputs regardless of the PUT, but neither does it require the time-consuming process of program analysis to create inputs. Instead, a greybox fuzzer uses a lightweight so called “guidance” to gain certain knowledge of the PUT, e.g., the code coverage. The intuition is that the fuzzer relies on a feedback loop: it tends to mutate and generate more inputs from those having higher coverage of the PUT. The child inputs generated from those with high code coverage are more likely to have high code coverage as well. Executing inputs with higher code coverage indicates that we can test more of the program paths, thus having a higher chance to find bugs.

A fuzzer’s knowledge of the PUT is only one way to classify fuzzers. Fuzzers can be categorized as mutation-based and generator-based fuzzers based on the input generation mechanisms. A mutation-based fuzzer, generates inputs by mutating the structures of a parent input. A generator-based fuzzer, creates inputs by specialized generators that can often create inputs with complex syntax, e.g., an XML file, HTML code, PNG, or PDF. For mutation-based fuzzers, it is generally believed and proved empirically that inputs mutated from “interesting” parent inputs are likely to be “interesting” as well, e.g., having high code coverage or satisfy certain conditions. Examples of mutation operations can be changing the byte values in the input or inserting magic values. The latter one, generator-based fuzzers, are often used to create syntatically correct or even semantically correct inputs. Why do we care about syntax? Well, many programs have a syntax check at beginning, for instance, if we feed a random string to an XML processing tool, the input will be rejected at the parsing stage without being executed by other functions in the tool. Therefore, it is crucial to have syntactically correct inputs in order to test other parts of the program.

Now that we learn about mutation-based and generator-based fuzzers, is there a way to combine these two approaches that can generate syntactically correct inputs while preserving the benefit of mutating from “interesting” parent inputs? The answer is YES, researchers have discovered a combined approach, parametric generators around 8 years ago. A parametric generator, like other generators, has conditional logics to generate the desired structures of inputs, e.g., a binary tree. However, the choice of values is backed by a pseudo random bitstring that can be mutated. For instance,

if random.nextBool() is True:
    generateLeftNode()

The bitstring used in the source of random to generate the values returned by nextBool() can be mutated as if it is a serialized string in mutation-based fuzzer. And the conditional controls the structures of the binary tree. In this way, we ensure the structure of the inputs generated via specialized generators, while being able to mutate the bitstrings that back the source of random used to create actual values or values at decision points.

Specialized Domains

It is normal to think that when we talk about testing, we refer to test code programs. However, fuzzing is applied not just to test programs, but more complicated systems such as API libraries, compilers, IoT devices, etc. One of the most commonly used algorithms in fuzzing is the feedback loop that awards generating inputs from those with “interesting” behaviors. Therefore, we can often formulate the abstract problem to be solved to fit into this feedback loop and use fuzzing to discover the intended behaviors. For example, if we want to find inputs with certain execution traces, we can use the similarity in execution traces as the feedback, and the more similar the traces are, the more positive feedback it has. Finding inputs with certain execution traces might be applicable to a variety of domains such as discovering buggy behaviors in IoT devices.

There is No Silver Bullet

One may ask which fuzzing technique is the best. The answer really depends on the actual problem and context, and there is no single, best way to resolve all. If the source code is not available, then people often choose blackbox or greybox fuzzing such as coverage-guided fuzzing. If the program is way too complicated or requiring highly structured inputs, then we might want to perform program analysis for whitebox fuzzing or use generator-based fuzzing to create specialized inputs.

As fuzzing has gained momentum in both research and industry nowadays, researchers and practitioners have invented various algorithms and applied state-of-the-art technologies such as deep learning/LLM in the fuzzing framework. To me, the most fascinating thing about fuzzing is that a seemingly simple, naive approach to test programs with random inputs can uncover complicated scenarios or bugs that human is ignorant of. With the acceleration of automation and the assistance of developers in the loop, fuzzing is a powerful technique that can not only verify programs but also discover interesting behaviors and patterns.
